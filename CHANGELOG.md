# Changelog

Notable changes to odyssey-core-orchestrator. Latest changes go at the top, under `[Unreleased]`, until a version is tagged.

## [Unreleased]

### Added
- The poison dead letter (gh-21): run requests the queue loop cannot act on — no envelope field, undecodable JSON, failed re-validation at the trust boundary — are dead-lettered to the new `odyssey:pipeline-requests-dead` stream and logged at warn, in the contract's `odyssey:jobs-dead`-style wrap (a `reason` of `decode` or `validation` plus the original envelope as `request`, or the raw entry bytes as `raw` when the envelope is not JSON); a failed dead-letter write is logged at error, surfaces as a loop error, and leaves the entry unacknowledged. The contract gains the stream additively (publisher orchestrator, consumer human inspection) with the 1,000-entry inspection trim, and publishing goes through a new consumer-owned `DeadLetterSink` seam satisfied by `*Publisher` (AUD-005).
- The logger seam (gh-21): a consumer-owned `Logger` interface (`Warn`/`Error`, satisfied by `*slog.Logger`) injected into the machine and both loops, a nil degrading to a discard logger. Every degraded path leaves a trace: `pipeline.started` and `pipeline.finished` emission failures are logged at warn with the run id, and the event loop logs malformed bus entries — no envelope field, undecodable JSON, a `job.finished` missing its coordinates or status — at warn, while other producers' event types and non-terminal status slugs stay silent by-design skips (AUD-005).
- Audit 1 (gh-19): the audit process (`audit/PROCESS.md`) and the first audit report (`audit/2026-10-17-0547-audit.md`, against `d4589e2`) are recorded in the repository — fifteen findings with evidence, tracked to resolution through the audit issue and its sub-issues.
- The event loop (gh-16): consumes the bus on a dedicated `orchestrator` consumer group created at `$` — the bus keeps other producers' history, and runs cannot predate this process, so it never replays. Job-finished events are re-validated at this boundary (coordinates present, terminal status slug) and drive the machine; malformed, foreign, and non-terminal events are acknowledged and skipped. A stage-release publish failure leaves the triggering event pending.
- Fail-fast tests (gh-16): the run-ending paths — a Failed or Errored stage ends the run with the worst status and no further releases, the decision waits for full stage resolution, outcomes for untracked runs are ignored, and a failed `pipeline.finished` emission leaves the ended run untracked. Note: these pin behavior that already shipped structurally with the JobFinished commit; the fail-fast paths were not driven red-first. Disclosed in the commit.
- Stage release and run completion (gh-16): `Machine.JobFinished` counts completions of the current stage; a stage resolving all-Passed releases the next stage under the same run id, and the last stage resolving Passed ends the run with `pipeline.finished` carrying `passed`. Concurrent runs sequence independently by run id. The decision waits for full stage resolution, matching the engine's recorded behavior (gh-82/AUD-015); worst-status ranking follows AUD-010 (errored worse than failed).
- `internal/orchestrator.Machine` (gh-16): the stage state machine ADR 0001 gives this repo ownership of — a mutex-guarded run table keyed by run id. `Start` emits `pipeline.started` and publishes only a run's first stage, holding the rest grouped per stage; a stage-1 publish failure rolls the run back out of the table.
- The orchestrator's queue loop (gh-14): consumes `odyssey:pipeline-requests` through a sole consumer group (`orchestrator`, ack on decision), and hands each contract-valid entry off as `pipeline.started` — emitted before any assignment, the results DB's parent-row invariant — followed by its stage-ordered assignments, under a fresh crypto-random run id per run. Entries that fail to decode or re-validate are poison: acknowledged, nothing published, the loop keeps serving. Emission failures degrade per the platform's policy (dispatcher repo ADR 0001); a publish failure leaves the entry pending. The loop runs until its context is cancelled. The two sinks are consumer-owned seams (`EventSink`, `AssignmentSink`) satisfied by the new `Emitter` and `Publisher`.
- The orchestrator's event emitter (gh-14): writes lifecycle events to `odyssey:events` in the dispatcher repo's `Event` envelope shape, field for field — `pipeline.started` carries `type`, `occurred_at`, `run_id`, `pipeline`, and no job, step, or payload — with the bus's approximate `MAXLEN` 100,000 trim and the platform's degradation policy left to the caller: emission failures never fail a run.
- The orchestrator's assignment publisher (gh-14): writes one entry per assignment to `odyssey:jobs` — single envelope field per the bus convention, approximate `MAXLEN` 100,000 trimming — and refuses at the wire any assignment failing the contract's § Job assignment field rules. Job-spec validation moved into a shared `pipeline.Job.Validate` so the config door and the assignment wire reject the same specs; config validation messages are unchanged.
- Agent guardrails in AGENTS.md: an explicit filesystem boundary (this repo, its parent `odyssey/` checkout, and their sub-folders only, reads and writes alike), tests-first development applying to every behavior slice, and tests as the source of truth — expected behavior through observable outputs and contract shapes, never implementation details.
- `internal/orchestrator` (gh-11): the pure segmentation slice — decodes a contract run-request envelope into the orchestrator's own consumer-side type (unknown fields ignored per additive evolution, no composer import), re-validates the envelope and the attached config at the trust boundary (shared rule set via the new `pipeline.Config.Validate`, so both boundaries reject the same pipelines with no TOML parser downstream), and turns a validated request plus a run id into contract-shaped job assignments: one per job, declared stage order, job names sorted within a stage (AUD-008), attempt 1, source carried through, job spec mirroring the resolved config, never outcomes. `Segment` documents the pipeline.started-before-any-assignment invariant at the segmentation site. No queue loop yet — that is the next work item.
- Process scaffolding: README with the architecture diagram and vocabulary, AGENTS.md conventions, RUNBOOK, docs-check gate, CI and issue/PR automation workflows, ship/merge scripts.
- ADR 0001: cluster orchestration — job-grain distribution, stateful stage state machine, feedback edge, failure modes, restart story.
- Dispatcher contract draft: streams, run request, job assignment, event emission responsibilities, delivery semantics.
- `internal/pipeline` (gh-5): parses and validates `.odyssey/pipeline.toml` into the contract's resolved configuration — TOML in, wire-shaped JSON out, `timeout` mapped to `timeout_ms`; every contract validation rule enforced and table-tested, all violations reported in one joined error, unknown keys rejected (parity with the dispatcher's config loader).
- The Go gate (gh-5): `go vet` / `go test ./...` / `go mod tidy -diff` / gofmt in `make check` and CI; RUNBOOK records the baseline.
- `internal/composer` (gh-7): the run request type with the contract's wire shape, envelope validation (origin enum, owner/repo slug, full 40-hex sha, non-empty trigger id and pipeline name — all violations in one error), and a publisher that writes single-envelope stream entries to `odyssey:pipeline-requests` with approximate MAXLEN trimming at the contract's default (10,000). Publish refuses invalid requests — the door holds at the wire.

### Changed
- Poison run requests are dead-lettered instead of silently skipped (gh-21): the gh-14 loop acknowledged undecodable and re-validation-failing entries and moved on with nothing published; it now wraps them with a reason on `odyssey:pipeline-requests-dead` first, still acknowledging and keeping the runs behind them flowing. `NewLoop` takes the dead-letter sink and the logger.
- The queue loop hands runs off to the machine (gh-16) instead of emitting and publishing itself: a run's hand-off is now `pipeline.started` plus its first stage only, with later stages waiting on `job.finished` events. `NewLoop` takes the machine.
- Scoped the README to this repo: the architecture diagram keeps only composer and orchestrator inside the repo boundary, with triggers, the dispatcher repo, the event bus, and downstream consumers as boundary nodes, and the reading notes restate dispatcher-side mechanics as boundary references. Cross-references now name `odyssey-ci-cd-platform/dispatcher` (the current location of the repo formerly named `odyssey-core-agent`).
- Recorded the branch-protection setup in RUNBOOK: protection on `main` applied at repository creation (required `check` status, admins enforced, no required approvals).
- Untracked `gates.json` and ignored it: it is machine-local harness configuration (its `allowPaths` carries home-directory paths), not repo content. It remains in early history from the bootstrap commit; removal from published history was not attempted.
- Dispatcher contract frozen by the field-by-field pass (gh-3): every run-request and assignment field pinned with type, semantics, and units; the resolved pipeline configuration schema added (composer fetches and attaches — ADR 0001's open question settled); `setup` added to the job spec so setup commands survive the boundary (a setup failure is job-level `errored`, mirroring the dispatcher's `SetupErr`); step timeouts pinned as `timeout_ms` with `0` = no timeout; dispatcher-side validation enumerated to match `internal/config`'s `Validate`; per-event payload fields pinned from the dispatcher's emission code; dead-letter stream `odyssey:jobs-dead` named; delivery parameters fixed as v1 defaults (30s renewal, 5m idle threshold, attempt limit 3, queue MAXLENs).
- Made the orchestrator origin-blind and the composer a separate service (gh-9): `origin` removed from the run request as a named contract revision (intake provenance is the composer service's concern; the orchestrator never sees which surface produced a run), `internal/composer` trimmed to the origin-free shape with the wire test asserting origin's absence, and README/AGENTS now describe an orchestrator-only repo. The composer repo is planned; `internal/composer` is its seed and migrates at that repo's bootstrap; services consolidate into a monorepo later.
