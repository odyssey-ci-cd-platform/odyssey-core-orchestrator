## Summary

The design documents are the strongest part of this repository: the ADR weighs real alternatives, and the contract pins every field with units and validation rules.
The code is a well-tested core with no service around it. There is no binary, no configuration, and no logger, so nothing here can be run.
The state machine is small and correct on its happy paths. But any transient Redis error, and any single lost `job.finished`, strands a run forever, because nothing retries pending entries and runs never time out.
The contract's own recovery path (a job reclaimed under a new `run_id`) contradicts the state machine it feeds.
The code already deviates from the contract in small ways (`stage` inside `job_spec`, an unchecked `pipeline` vs `config.pipeline` pair), and no test pins the wire shapes against the contract's examples.

## New findings

### AUD-001 — A transient publish failure strands a run forever

- **Severity:** Critical
- **Category:** correctness
- **Verification:** Confirmed
- **Location:** `internal/orchestrator/machine.go:148-172`, `internal/orchestrator/loop.go:80,96`, `internal/orchestrator/eventloop.go:53,69`
- **Problem:** `JobFinished` advances the run (`r.next++`, `r.pending` replaced by the next stage) under the lock before it publishes that stage. If the publish fails, the error propagates "so the entry stays pending". But (1) a redelivered event finds the job no longer pending and returns nil, and (2) nothing ever redelivers: both loops read only `>` (new entries) and never `XAUTOCLAIM` or re-read their own PEL, and both loops exit on the first error with no retry. The same holds for a stage-1 publish failure in `Loop.handOff`. The doc comments ("leaves the entry unacknowledged", "the entry stays pending") imply a retry that does not exist. Stage sequencing is the job ADR 0001 gives this repository, and it does not survive one Redis blip.
- **Failure scenario:** Measured with fakes: stage `build` passes, the release of `test` fails once with `redis down`, and the redelivered `job.finished` returns nil. Afterwards the run is still tracked with `pending={b}` and `next=2`, but `b` was never published. Measured with miniredis: a run request whose first publish fails leaves `pendingCount=1` after a loop restart, with nothing published. Each such run never finishes and stays in memory.
- **Suggested fix:** Commit the state transition only after the publish succeeds, or make release idempotent by keying on `(run, stage)`. On start, re-read the group's own pending entries (`XREADGROUP … 0`) or claim them. Retry transient errors with backoff instead of returning from `Run`.

### AUD-002 — The service has no binary and cannot be run

- **Severity:** High
- **Category:** architecture
- **Verification:** Confirmed
- **Location:** repository root (no `cmd/`, no `func main`), `internal/orchestrator/loop.go:56`, `internal/orchestrator/eventloop.go:29`, `internal/orchestrator/machine.go:43`, `README.md` (Architecture)
- **Problem:** README describes a running service that consumes run requests, publishes assignments, and consumes `job.finished`. `NewLoop`, `NewEventLoop`, and `NewMachine` are never wired together outside tests. There is no Redis address, configuration, logger, signal handling, or shutdown. Everything listed in CHANGELOG `[Unreleased]` is library code that no process runs.
- **Failure scenario:** A run request published to `odyssey:pipeline-requests` is never consumed by anything that can be started.
- **Suggested fix:** Add `cmd/orchestrator` with env-based configuration, a logger, one signal context driving both loops, and an end-to-end smoke script against live Redis. The dispatcher repo's `scripts/e2e-event-bus.sh` is the reference shape.

### AUD-003 — One lost `job.finished` hangs a run forever; runs never time out

- **Severity:** High
- **Category:** architecture
- **Verification:** Plausible
- **Location:** `internal/orchestrator/machine.go:23-39,134-175`, `docs/adr/0001-cluster-orchestration.md` (Decision 2, Decision 6), `docs/contracts/dispatcher-contract.md` (Event emission responsibilities)
- **Problem:** ADR 0001 makes `job.finished` on the event bus the binding feedback edge. The same ADR calls the bus "lossy and never replayed", and the contract adopts the producers' policy that emission failures never fail a run. The contract imposes no delivery guarantee on `job.finished`. The machine has no run deadline, no job deadline, no reaper, and no cancellation, so its `runs` map grows with every run whose outcome never arrives.
- **Failure scenario:** One `job.finished` is lost (a failed `XADD` at the producer, or stream trimming while this group lags). The stage never resolves, `pipeline.finished` is never emitted, and the run stays in memory until the process restarts. The restart then loses every in-flight run (Decision 6).
- **Suggested fix:** Make the contract require at-least-once delivery for `job.finished` (producer retries until written), or derive completion from the job queue ack. Add a per-run deadline that resolves the run as `errored`, emits `pipeline.finished`, and evicts it. Expose the in-flight run count.

### AUD-004 — The contract's reclaim semantics contradict the state machine

- **Severity:** High
- **Category:** architecture
- **Verification:** Plausible (by reading the documents against the code)
- **Location:** `docs/contracts/dispatcher-contract.md:89-90,122`, `docs/adr/0001-cluster-orchestration.md:44`, `internal/orchestrator/machine.go:142-146`
- **Problem:** The contract says a job reclaimed from a dead dispatcher "re-executes from scratch under a new `run_id`". The ADR says the *run* re-executes under a new run id. Run ids are minted only by this repository, and the machine ignores events for run ids it did not mint. So the documented recovery path guarantees the original run never resolves (AUD-003). The re-executed job also has no `pipeline.started` for its new run id, which breaks the parent-row invariant README calls "load-bearing". The two documents also disagree on whether the unit of retry is the job or the run.
- **Failure scenario:** A dispatcher dies mid-job. A peer reclaims the assignment and re-runs it under run id `X'`. The machine ignores every outcome for `X'`, and run `X` waits forever.
- **Suggested fix:** Keep the run id stable across attempts and distinguish attempts by the `attempt` field, which the contract already defines. Make the ADR and the contract state one retry unit, and teach the machine how an `attempt > 1` outcome replaces the first.

### AUD-005 — Run requests and errors are discarded without a trace

- **Severity:** High
- **Category:** correctness
- **Verification:** Confirmed (by code and `TestLoopSkipsPoisonEntries`)
- **Location:** `internal/orchestrator/loop.go:111-129`, `internal/orchestrator/eventloop.go:84-108`, `internal/orchestrator/machine.go:69-78,201-212`
- **Problem:** A run request that fails to decode or validate is acknowledged and dropped, with no log, no metric, and no dead-letter. The contract requires that assignments are "never silently dropped" and gives them `odyssey:jobs-dead`, but defines nothing equivalent for requests. The composer is fire-and-forget by design, so the user's run simply vanishes. Every emission error is discarded with `_ = err` and the comment "v1 has no logger". The package has no logger at all, so failures of `pipeline.started` (which README says the parent-row invariant depends on) and `pipeline.finished` are invisible.
- **Failure scenario:** A composer and orchestrator a version apart disagree on a field rule. Every run request is acknowledged and discarded, and nothing anywhere records why runs stopped happening.
- **Suggested fix:** Add `odyssey:pipeline-requests-dead` to the contract, with a reason, mirroring `odyssey:jobs-dead`. Inject an `*slog.Logger` and log every degraded path.

### AUD-006 — The code deviates from its own contract, and no test pins the wire shapes

- **Severity:** Medium
- **Category:** correctness
- **Verification:** Confirmed
- **Location:** `internal/orchestrator/orchestrator.go:43-63,95`, `internal/pipeline/pipeline.go:29,43-46,116-119`, `internal/composer/runrequest.go:34-50`, `internal/composer/publish.go:37-39`, `internal/orchestrator/emit.go:38-50`, `docs/contracts/dispatcher-contract.md:96-101`
- **Problem:**
  - `job_spec` carries `"stage"` on the wire (measured: `{"stage":"build","image":"alpine",…}`), though the contract says stage "rides the assignment envelope, not the spec".
  - Neither `RunRequest.Validate` (orchestrator or composer) checks that `pipeline` equals `config.pipeline`, a contradictory pair the design principles say to reject.
  - The composer's `Publish` validates only the envelope, not the attached config, despite "the door holds at the wire".
  - The contract asserts its dispatcher-side rules "are the same rules `internal/config`'s `Validate` applies", and `pipeline.go` says the two "must not drift", but nothing in this repository can check either claim.
  - `TestSegmentMarshalsContractShape` checks only that keys are present, not that unexpected keys are absent.
  - The emitted envelope is a hand-written struct, "matching the dispatcher repo's internal/domain Event JSON field for field", with no fixture to compare against.
- **Failure scenario:** A request with `pipeline = "a"` and `config.pipeline = "b"` is accepted and segmented under `a`. A consumer that rejects unknown `job_spec` fields rejects every assignment.
- **Suggested fix:** Drop `stage` from the marshalled spec (a separate wire type for `job_spec`), cross-check the pipeline names, and validate config in `Publish`. Turn the contract's JSON examples into golden fixtures that tests round-trip exactly. Ship the fixtures (or a JSON Schema) as the artifact other repositories test against, instead of prose parity claims.

### AUD-007 — The service assumes a single instance without enforcing it, and dies on transient errors

- **Severity:** Medium
- **Category:** architecture
- **Verification:** Plausible (by code reading)
- **Location:** `internal/orchestrator/loop.go:20-27,79,96`, `internal/orchestrator/eventloop.go:33-44,52,64`
- **Problem:** Both loops return on the first Redis error with no backoff or retry, which (once wired, AUD-002) takes down the process and every in-memory run. The consumer name is the constant `orchestrator`, so two replicas would act as one consumer and split events between machines that each know only their own runs. Nothing enforces the documented "one orchestrator process" (no lock or lease). The `$` start of the events group protects only the first-ever start; after a restart the group resumes and replays events for runs the new process never started. That is harmless, but it contradicts the comment that runs "cannot predate this process".
- **Failure scenario:** A Redis failover blip: both loops return errors, the process exits, and every in-flight run is lost.
- **Suggested fix:** Retry with bounded backoff. Take a Redis lease for single-instance operation. Use per-instance consumer names, and fix the comment.

### AUD-008 — The contract carries secrets in plaintext and assumes an unauthenticated Redis

- **Severity:** Medium
- **Category:** security
- **Verification:** Plausible (by reading the contract)
- **Location:** `docs/contracts/dispatcher-contract.md` (Resolved pipeline configuration, `env` rule; Streams), `internal/orchestrator/publish.go`, `internal/composer/publish.go`
- **Problem:** The contract says `env` values "are literal strings (secret interpolation is not this contract's concern)". So every secret a pipeline needs travels in plaintext through `odyssey:pipeline-requests` and `odyssey:jobs`, and copies persist up to the `MAXLEN` bound and in `odyssey:jobs-dead`. The contract says nothing about Redis authentication or TLS, so anyone who can write the queues can inject assignments that run arbitrary images.
- **Failure scenario:** A read-only Redis credential leaked for debugging exposes every pipeline's secrets.
- **Suggested fix:** Carry secret references, not values, and resolve them at execution time. Add a security section to the contract: Redis ACLs per stream, TLS, and who may publish to each queue.

## Strengths

- ADR 0001 is exemplary: real alternatives, explicit rejections with reasons, failure modes split by ownership, and revisit triggers.
- The contract pins every field with type, units, validation, and defaults, and it states its evolution rule (additive only).
- Trust-boundary re-validation is applied consistently: the composer validates at publish, the orchestrator re-validates at consume, and the assignment publisher refuses invalid assignments at the wire.
- The state machine is small, mutex-guarded, deterministic in ordering, and tested over concurrent runs.
- One `make check` gate (docs, vet, test, tidy, gofmt) behind protected `main`, with SHA-pinned actions.
- The CHANGELOG honestly discloses where tests-first was not followed.

## Recommended order

1. AUD-001: commit state only after a successful publish, and recover pending entries.
2. AUD-002: a binary with configuration and a logger, plus an end-to-end smoke script.
3. AUD-003 and AUD-004: a reliable feedback edge, run deadlines, and one coherent retry model in the ADR and the contract.
4. AUD-005: dead-letter and log discarded requests.
5. AUD-006: golden contract fixtures, so the boundary is tested rather than asserted.
6. AUD-010: failure-path tests for everything above.
